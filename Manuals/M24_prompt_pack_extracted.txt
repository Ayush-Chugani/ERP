1. Source Schema
CREATE TABLE faculty_internship (
    staff_activity_id BIGINT UNSIGNED PRIMARY KEY,
    organization_id BIGINT UNSIGNED NOT NULL,
    internship_title VARCHAR(500) NOT NULL,
    internship_domain VARCHAR(250) NULL,
    industry_sector_id SMALLINT UNSIGNED NULL,
    location_text VARCHAR(300) NULL,
    mentor_name VARCHAR(200) NULL,
    mentor_designation VARCHAR(150) NULL,
    mentor_email VARCHAR(254) NULL,
    work_undertaken TEXT NULL,
    technologies_tools TEXT NULL,
    outcomes TEXT NULL,
    stipend_incentive_type ENUM(
        'NONE','STIPEND','INCENTIVE','HONORARIUM','OTHER'
    ) NOT NULL DEFAULT 'NONE',
    stipend_incentive_amount DECIMAL(14,2) NULL,
    currency_code CHAR(3) NOT NULL DEFAULT 'INR',
    funding_source VARCHAR(250) NULL,
    mou_reference VARCHAR(150) NULL,
    collaboration_reference VARCHAR(250) NULL,
    CONSTRAINT chk_faculty_internship_amount CHECK (
        stipend_incentive_amount IS NULL OR stipend_incentive_amount >= 0
    ),
    CONSTRAINT fk_faculty_internship_activity FOREIGN KEY (staff_activity_id)
        REFERENCES staff_activity(staff_activity_id),
    CONSTRAINT fk_faculty_internship_org FOREIGN KEY (organization_id)
        REFERENCES external_organization(organization_id),
    CONSTRAINT fk_faculty_internship_sector FOREIGN KEY (industry_sector_id)
        REFERENCES industry_sector(industry_sector_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
2. Architecture and Implementation Guardrails
faculty_internship is a strict one-to-one subtype of staff_activity; staff_activity_id is both its primary key and foreign key.
Reuse existing staff_activity, external_organization, industry_sector, employee, academic-year, institution, campus, department, document, audit, notification, and workflow components.
Use the configured Django custom user model and existing role/permission framework. Never introduce a parallel authentication system.
Keep business rules in services/domain logic; serializers/forms validate input; views/API controllers orchestrate requests.
Use transaction.atomic() for parent/subtype creation and workflow transitions.
Use server-side object-level authorization. Never trust organizational scope or employee identity sent by the browser when it can be derived from the authenticated user.
Use MySQL/InnoDB/utf8mb4, reversible migrations, query optimization, and database constraints.
Build a responsive, accessible, mobile-first PWA; support intermittent networks without duplicating writes or leaking sensitive cached data.
Use the shared attachment service for evidence. Do not add file/blob columns to faculty_internship.
Historical institutional records should not be cascade-deleted unless the wider SIMS retention policy explicitly requires it.

4. Acceptance Criteria
One faculty_internship exists for at most one staff_activity, with the same identifier used as the subtype primary key.
Create/update operations cannot leave orphaned or partially created parent/subtype data.
Only authorized users can view or modify records within their permitted organizational scope.
All source-schema fields are represented with correct validation and MySQL-compatible persistence.
Organization and industry sector are reused from existing master data.
Internship dates and common staff metadata remain in staff_activity and are not duplicated.
PWA forms and views are mobile-first, accessible, responsive and robust under slow/intermittent networks.
Evidence uses the shared attachment system and is protected by object-level authorization.
Reports/exports enforce the same authorization scope as interactive screens.
Backend/frontend automated tests cover business rules, permissions, workflows, security and critical UI behavior.
No unjustified schema duplication, redundant index, N+1 query, insecure direct-object access or destructive historical cascade remains.

6. Important Implementation Note
The supplied SQL intentionally keeps internship-specific attributes in faculty_internship and common staff activity attributes in staff_activity. The Django implementation should preserve this supertype/subtype design. If the existing SIMS codebase already provides generic workflow, audit, attachment, export, master-data, or notification capabilities, extend those facilities rather than building module-specific replacements.
