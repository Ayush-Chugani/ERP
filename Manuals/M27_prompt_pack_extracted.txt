Implementation Prompt Pack
27. CONSULTANCY / INDUSTRY-SPONSORED PROJECT
Enterprise Django • Django REST Framework • MySQL • Progressive Web Application
This document provides a sequential set of AI development prompts for implementing the Consultancy / Industry-Sponsored Project module as a specialization of the Staff Activity subsystem. It covers schema mapping, transactions, workflow, financial integrity, APIs, security, PWA screens, reporting, testing, performance, deployment, and recommended normalized extensions.
1. Supplied Core Database Schema
CREATE TABLE consultancy_project (    staff_activity_id BIGINT UNSIGNED PRIMARY KEY,    consultancy_title VARCHAR(500) NOT NULL,    client_organization_id BIGINT UNSIGNED NOT NULL,    principal_consultant_employee_id BIGINT UNSIGNED NOT NULL,    consultancy_type ENUM('CONSULTANCY','INDUSTRY_SPONSORED_PROJECT',        'TESTING_SERVICE','TRAINING_SERVICE','OTHER')        NOT NULL DEFAULT 'CONSULTANCY',    work_order_number VARCHAR(150) NULL,    agreement_number VARCHAR(150) NULL,    purchase_order_number VARCHAR(150) NULL,    project_start_date DATE NOT NULL,    completion_date DATE NULL,    consultancy_amount DECIMAL(16,2) NOT NULL DEFAULT 0.00,    amount_received DECIMAL(16,2) NOT NULL DEFAULT 0.00,    faculty_incentive_share DECIMAL(16,2) NULL,    currency_code CHAR(3) NOT NULL DEFAULT 'INR',    deliverables TEXT NULL,    status ENUM('PROPOSED','APPROVED','ONGOING','COMPLETED','CANCELLED','CLOSED')        NOT NULL DEFAULT 'PROPOSED',    client_feedback TEXT NULL,    CONSTRAINT chk_consultancy_dates CHECK (        completion_date IS NULL OR completion_date >= project_start_date    ),    CONSTRAINT chk_consultancy_amounts CHECK (        consultancy_amount >= 0 AND amount_received >= 0        AND (faculty_incentive_share IS NULL OR faculty_incentive_share >= 0)    ),    CONSTRAINT fk_consultancy_activity FOREIGN KEY (staff_activity_id)        REFERENCES staff_activity(staff_activity_id),    CONSTRAINT fk_consultancy_client FOREIGN KEY (client_organization_id)        REFERENCES external_organization(organization_id),    CONSTRAINT fk_consultancy_principal FOREIGN KEY (principal_consultant_employee_id)        REFERENCES employee(employee_id)) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
2. Architectural Rules
Treat consultancy_project as a strict subtype of staff_activity: the child primary key is the parent staff_activity_id.
Reuse existing Employee, ExternalOrganization, Institution, Department, Academic Year, attachment, audit, and RBAC infrastructure; do not duplicate master data.
Use Django DecimalField/Decimal for money and preserve MySQL DECIMAL precision.
Create/update parent and child records atomically in a service layer.
Enforce critical rules at both database and application layers.
Use versioned DRF APIs and a mobile-first React/TypeScript PWA.
Server-side authorization is mandatory; UI visibility is not a security control.
Do not silently change the supplied core schema. Proposed extensions require explicit migrations.
3. Recommended Enterprise Extensions
Project team/co-consultants and their roles.
Structured milestones/deliverables and acceptance tracking.
Receipts/installments and invoice/payment references.
Project documents: proposal, work order, agreement/MoU, PO, invoice, completion certificate and client feedback evidence.
Status/approval history and complete audit trail.
Optional institutional overhead, GST/tax, department share and faculty incentive distribution, only when institutional rules are confirmed.
Indexes for client, principal consultant, status, type and project dates after query-plan/workload review.
4. Sequential Development Prompts
Prompt 1 — Analyze the Existing SIMS Architecture
Act as the lead architect for an existing enterprise SIMS using Django, DRF, MySQL and React/TypeScript PWA. Inspect the repository before coding. Identify the StaffActivity subtype pattern, exact Employee and ExternalOrganization models, activity-type master data, authentication/RBAC, audit logging, attachments, API conventions, filtering/pagination, frontend routing/state management, tests, CI and deployment conventions. Produce a file-by-file implementation plan for Module 27. Reuse existing infrastructure and do not create duplicate master models. Identify migration risks and assumptions.
Prompt 2 — Implement the Django Model
Implement ConsultancyProject mapped to db_table='consultancy_project' exactly as supplied. Use a OneToOneField to StaffActivity as primary_key=True, FKs to ExternalOrganization and Employee, TextChoices for consultancy_type/status if compatible with the project, DecimalField(max_digits=16, decimal_places=2), currency_code default INR, and exact nullability/max lengths. Add database CheckConstraint equivalents for dates and non-negative money plus clean()/domain validation. If the table already exists, propose a non-destructive migration/mapping strategy. Add model and constraint tests.
Prompt 3 — Atomic Create Service
Create a transactional service that creates StaffActivity and ConsultancyProject together using transaction.atomic(). Validate the correct activity type, authorized/active client and employee references, completion_date >= project_start_date, non-negative monetary values, uppercase three-character currency code and all required parent fields. Roll back the StaffActivity if child creation fails. Keep business logic out of views. Add success, validation and rollback tests.
Prompt 4 — Update, Archive/Delete and Concurrency
Implement transactional update and archive/delete services. Update parent StaffActivity and child ConsultancyProject consistently. Use select_for_update() or the project's established optimistic locking for sensitive status/financial edits. Follow existing soft-delete/archive policy where available. Protect referenced master data. Emit domain-friendly validation errors and audit important changes. Test concurrent edits, rollback and authorization.
Prompt 5 — Status Workflow
Implement a centralized state machine for PROPOSED, APPROVED, ONGOING, COMPLETED, CANCELLED and CLOSED. Define an explicit transition map consistent with institutional workflow. Prevent arbitrary status changes. Require valid dates; normally require completion_date for COMPLETED/CLOSED. Decide and document whether CLOSED requires COMPLETED plus administrative/financial closure. Record transition actor, timestamp and remarks using existing audit/history infrastructure or a normalized history table if approved. Add transition and permission tests.
Prompt 6 — Financial Integrity
Implement Decimal-based financial logic for consultancy_amount, amount_received and faculty_incentive_share. Preserve the supplied non-negative rules. Do not assume amount_received <= consultancy_amount or incentive <= receipts unless institutional policy explicitly requires it. Provide read-only derived metrics such as balance_receivable and collection_percentage with safe zero handling. Format currency only at presentation time. Test zero, partial, full, large-value, rounding and policy-dependent over-receipt cases.
Prompt 7 — DRF Serializers
Create compact list, detailed read, create, update and status-transition serializers. Read serializers should expose useful client/principal-consultant display data without N+1 queries. Write serializers should accept IDs and invoke service-layer operations. Validate dates, money, choices, currency, object activity/visibility and authorization. Keep server-controlled fields read-only and use the project's standard error envelope.
Prompt 8 — REST API
Implement versioned DRF endpoints for list, create, retrieve, update, archive/delete and controlled status transition. Add pagination, deterministic ordering, search and filters for status, consultancy_type, client, principal consultant, project date range, and StaffActivity institution/department/academic-year fields where available. Search title, work order, agreement, purchase order, client and consultant names. Optimize with select_related/prefetch_related and document endpoints in the project's OpenAPI tooling.
Prompt 9 — RBAC and Object-Level Security
Implement server-side permissions for view, create, edit, status transition, financial edit, document management and archive/delete. Scope querysets by institutional role, department and ownership according to the existing RBAC model. Prevent IDOR/horizontal privilege escalation and unauthorized foreign-key assignment. Never rely on disabled frontend controls. Add negative authorization tests for every protected action.
Prompt 10 — Project Team Extension
Design an optional normalized project-team table for co-consultants. Keep principal_consultant_employee_id in the core table authoritative. Suggested fields: project FK, employee FK, project_role, contribution_description, start/end dates, is_active and optional incentive allocation only if policy is confirmed. Prevent duplicate active membership and validate dates. First present proposed SQL/Django schema and migration; then implement model, API, UI and tests after approval.
Prompt 11 — Milestones and Deliverables
Design an optional normalized milestone/deliverable model while retaining consultancy_project.deliverables as high-level scope text. Suggested fields: project FK, sequence, title, description, due_date, completion_date, status, acceptance_date and client_remarks. Build CRUD API, permissions, progress/overdue indicators and tests. Validate dates against project boundaries where appropriate. Do not modify the database without an explicit migration.
Prompt 12 — Receipts and Financial Ledger
Design a normalized receipt/installment model because amount_received alone cannot provide transaction history. Suggested fields: project FK, receipt_date, amount, currency_code, reference_number, invoice_number, payment_mode/reference, tax/deduction values if required, remarks and document attachment. Update the aggregate amount_received transactionally from ledger records if the architecture adopts a ledger source of truth. Never use float. Add reconciliation, duplicate-reference protection, authorization and financial tests.
Prompt 13 — Document Management
Integrate the project's secure document/attachment framework for proposal, work order, agreement/MoU, purchase order, invoices, completion certificate, client feedback and other evidence. Validate file type/size, generate safe storage names, prevent path traversal, enforce access permissions and preserve audit metadata. Do not expose private storage paths. Add upload/download/delete APIs and tests if not already provided by a common attachment module.
Prompt 14 — React/TypeScript PWA Screens
Build mobile-first PWA screens for consultancy projects: dashboard/list, filters/search, create/edit form, project detail, status timeline, financial summary, deliverables/milestones, team, documents and client feedback where enabled. Use dependent master-data selectors, date pickers, Decimal-safe amount inputs, validation messages, loading/empty/error states and accessible controls. Hide actions the user cannot perform but still rely on server authorization. Reuse the project's design system.
Prompt 15 — Offline and PWA Behavior
Implement safe PWA behavior. Cache the application shell and non-sensitive reference data using the existing service-worker strategy. Do not broadly cache confidential project/financial API responses. If offline drafts are permitted, store only necessary form data, clearly mark unsynced drafts, retry safely and resolve conflicts explicitly. Never queue destructive/status/financial actions blindly. Provide installability, update notification and network-state UX.
Prompt 16 — Dashboard and Reports
Implement dashboard metrics and exportable reports without inventing policy conclusions. Include counts by status/type, sanctioned consultancy value, amount received, receivable balance, active/completed projects, client distribution, department/institution breakdown and date-period filters as permitted by data scope. Use aggregate queries efficiently. Provide CSV/XLSX/PDF export only through existing report infrastructure, enforce permissions and protect against formula injection in spreadsheet exports.
Prompt 17 — Validation and Edge Cases

5. Suggested Acceptance Criteria
A consultancy project cannot exist without exactly one valid StaffActivity parent.
Parent and child create/update operations are atomic.
Client and principal consultant must reference valid master records.
Invalid dates and negative financial values are rejected at application and database levels.
Status changes use controlled transitions and are auditable.
Financial values use Decimal end-to-end.
List/detail APIs are permission-scoped, paginated and query-optimized.
PWA forms work on mobile layouts and provide accessible validation feedback.
Sensitive data is not insecurely cached by the service worker.
Automated tests cover model, service, API, workflow, security and regression behavior.
Production migrations are reviewed, reversible where practical, and backed up.
6. Key Policy Decisions to Confirm Before Finalization
Whether amount_received may exceed consultancy_amount.
Whether faculty_incentive_share is a monetary amount, percentage, or both through a separate allocation model.
Whether COMPLETED requires full payment and whether CLOSED represents financial/administrative closure.
Whether work order/agreement/purchase order numbers must be unique and at what institutional scope.
Required GST/tax, institutional overhead and revenue-sharing rules.
Whether multiple consultants/team members and incentive distribution must be formally tracked.
Mandatory documents and approval authorities for each consultancy type.
Retention, archival and deletion policy for completed/cancelled projects.
