Module 34 Document Evidence Requirement Configuration Prompt Pack
Implementation prompts for a Django, MySQL and Progressive Web Application module that defines the evidence expected for each staff activity type. Run the prompts in order against the existing SIMS repository. Each prompt asks for working code, migrations and focused verification while preserving established project conventions.
Shared implementation context
Target table: activity_evidence_requirement. Columns: activity_evidence_requirement_id BIGINT UNSIGNED auto primary key; activity_type_id SMALLINT UNSIGNED required; evidence_type_id SMALLINT UNSIGNED required; document_type_id SMALLINT UNSIGNED nullable; is_mandatory BOOLEAN default FALSE; minimum_files TINYINT UNSIGNED default 0; maximum_files TINYINT UNSIGNED nullable; valid_from and valid_to nullable DATE; is_active BOOLEAN default TRUE. Foreign keys reference activity_type, evidence_type and document_type. The supplied SQL names its unique constraint uq_activity_evidence_requirement and its checks chk_activity_evidence_file_counts and chk_activity_evidence_requirement_dates.
Important MySQL behavior: a UNIQUE key on (activity_type_id, evidence_type_id, document_type_id) permits multiple rows where document_type_id is NULL. The supplied key also prevents a second dated version for the same nonnull combination. Resolve both policy questions before extending versioning; do not silently claim that this constraint enforces either unique NULL rows or historical versions.

Prompt 3 Domain model and validation
Create the Django model and validation/service rules for minimum_files 0..255, maximum_files nullable 0..255 and >= minimum_files, and valid_to >= valid_from when both dates exist. Decide and document the operational meaning of is_mandatory with minimum_files=0; recommend treating mandatory as at least one effective required file, enforced centrally, or reject the ambiguous combination if product policy chooses that route. Validate foreign-key choices, active flags and any document/evidence type compatibility already defined in SIMS. Keep database CHECK constraints as the final integrity layer. Acceptance: invalid values fail cleanly through forms/API and database writes; valid boundary values work.
Prompt 4 Uniqueness and effective date policy
Propose a concrete policy and implement it after confirmation in the project: either configuration has one row per activity/evidence/document combination, with dates defining the row’s validity, or the schema is revised for nonoverlapping historical versions. Demonstrate MySQL nullable UNIQUE behavior and prevent duplicate rows with document_type_id NULL using a database enforceable approach supported by the deployed MySQL version (for example a generated normalized key plus unique index), with application validation as a helpful additional layer. If historical versions are required, provide a separate migration strategy and prevent overlapping effective intervals, including concurrent writes. Do not present a plain Django UniqueConstraint on nullable document_type as sufficient. Acceptance: concurrent duplicate NULL inserts cannot both succeed and the documented versioning policy matches the schema.
Prompt 5 Requirement resolution service
Build a reusable service that returns active requirements for an activity type as of a requested date, with explicit inclusive valid_from/valid_to semantics and null bounds treated as open intervals. Query efficiently, avoid N+1 reads, and return deterministic ordering. Make evidence_type_id and optional document_type_id matching rules explicit, including whether NULL means any document type or an unspecified document type; select one policy based on existing Module 33 behavior and document it. Do not infer required files from historical inactive rows. Acceptance: boundary-date, inactive, null-bound and matching tests pass.
Prompt 6 Evidence compliance integration

Use transaction-safe counting/locking or revalidation where concurrent uploads can exceed maximum_files. Acceptance: finalization blocks only on enforceable unmet rules; counts change correctly as documents are added or removed.
