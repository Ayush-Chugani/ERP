1. Purpose and Scope
This prompt pack converts the supplied SQL for Module 10 into an implementation blueprint suitable for an enterprise-grade Django SIS. It is designed to preserve the SQL ownership constraints, transaction boundaries, custom-user authorization model, and plugin-ready modular-monolith structure established in the earlier modules.
Configure continuous-assessment components for a course offering.
Create one or more assessment events under each component.
Capture student attendance status and marks for each assessment event.
Maintain institution-wide grade scales and percentage-to-grade rules.
Compute and publish course-level results for every attempt.
Compute and publish term-level credits, SGPA, CGPA, and overall status.
Expose secure REST APIs and React/MUI pages for faculty, exam/result staff, students, and administrators.
Preserve auditability, validation, concurrency safety, and controlled publication.

3. Architectural Rules to Preserve
Keep Module 10 isolated as an academic-results domain package while reusing identities and registrations from earlier modules.
Do not duplicate student, course, term, section, or user master data inside this module.
Use service-layer commands for result calculation, publication, recalculation, and bulk mark entry.
Use Django custom-user authorization with explicit permissions; never infer authority only from frontend role labels.
Use database transactions for bulk mark entry, result generation, grade assignment, and publication.
Preserve composite ownership rules expressed by foreign keys such as (assessment_event_id, course_offering_id) and (course_registration_id, course_offering_id).
Use immutable/audited publication behavior: published results may be corrected only through an authorized controlled workflow.
Keep API serializers thin; place cross-record academic rules in domain validators/services.
Expose result data to students only after publication and only for their own registrations.
Add audit events for marks edits, grade-rule changes, result calculation, result withholding, publication, and corrections.

5. Recommended Django App Structure
PROMPT 10.1 - Create the Module Package
Act as a senior Django architect. Create a plugin-ready modular-monolith package named `assessments_results` for the SIS.Use Django 5.x and DRF. The app must contain: `models/`, `services/`, `selectors/`, `api/serializers/`, `api/views/`, `api/urls.py`, `permissions.py`, `validators.py`, `admin.py`, `tests/`, and `migrations/`.Dependencies may point only to established SIS modules such as course offerings, student term registration, student course registration, employees/faculty, and the custom user model. Avoid circular imports by using string model references where appropriate.Create service classes/functions for assessment setup, bulk mark entry, grade-scale maintenance, course-result calculation, term-result calculation, result publication, withholding, and correction. Keep cross-record business logic out of serializers and ViewSets.

6. Django Models - Assessment Setup
PROMPT 10.2 - Implement AssessmentComponent
Implement a Django model matching `assessment_component` exactly in meaning.Fields: assessment_component_id, course_offering FK, component_code, component_name, component_type choices, maximum_marks, weightage_percent, is_mandatory.Requirements:- preserve unique `(course_offering, component_code)`;- preserve ownership uniqueness `(assessment_component_id, course_offering_id)` where needed for composite ownership compatibility;- validate maximum marks and weightage;- add useful indexes for course offering and component type;- provide `__str__` and admin search/filter configuration;- expose no direct student write access.

PROMPT 10.3 - Implement AssessmentEvent
Implement `AssessmentEvent` corresponding to `assessment_event`.It belongs to one AssessmentComponent and one CourseOffering. Validate that both refer to the same owning course offering. Support event_number, event_title, assessment_date, optional start/end times, maximum_marks, optional reduced_maximum_marks, details, and lifecycle status PLANNED/CONDUCTED/CANCELLED/PUBLISHED.Rules:- end_time must be later than start_time when both are present;- reduced maximum must not exceed event maximum;- event maximum should normally be compatible with the parent component maximum according to configurable policy;- only authorized academic staff may change status;- once PUBLISHED, structural changes require an explicit reopen/correction workflow.

7. Django Model - Student Assessment Marks
PROMPT 10.4 - Implement StudentAssessmentMark
Implement `StudentAssessmentMark` matching the SQL fields and unique rule `(assessment_event, course_registration)`.The record must also carry course_offering and validate ownership against both the assessment event and the course registration.Attendance choices: PRESENT, ABSENT, EXEMPTED, MALPRACTICE.Implement validation rules for marks_obtained and reduced_marks. Do not accept negative values. Validate upper bounds against the selected assessment event. Define policy hooks for ABSENT, EXEMPTED, and MALPRACTICE. Set evaluated_at only when evaluation is committed.Create a service method for bulk upsert of marks that runs in `transaction.atomic()`, locks the targeted event if required, validates the whole batch, and either commits all valid rows or returns row-level validation errors without a partial academic result.

8. Grade Scale and Grade Rules
PROMPT 10.5 - Implement GradeScale and GradeRule
Create GradeScale and GradeRule Django models corresponding to the supplied SQL.GradeScale: name, effective_from, effective_to, is_active.GradeRule: grade_scale FK, grade_letter, grade_point, minimum_percentage, maximum_percentage, result_status.Add validators so percentages stay within 0..100, maximum >= minimum, grade point is non-negative, and effective_to is not earlier than effective_from.At service level, prevent overlapping percentage bands inside the same grade scale. Provide `resolve_grade(grade_scale, percentage)` that returns exactly one rule or raises a controlled configuration error. The function must be deterministic, unit-tested, and safe at exact range boundaries.

9. Course Result Model and Calculation Service
PROMPT 10.6 - Implement StudentCourseResult
Implement StudentCourseResult with one row per `(course_registration, attempt_number)`.Fields: internal_marks, external_marks, total_marks, grade_letter, grade_point, credits_earned, result_status, result_date, remarks.Create a `CourseResultService.calculate()` method that receives a course registration, attempt number, applicable grade scale, and institutional calculation policy. It should:1. validate registration eligibility;2. collect internal assessment evidence;3. incorporate external marks when applicable;4. calculate normalized total/percentage according to policy;5. resolve grade using the active grade scale;6. determine credits earned;7. support ABSENT/WITHHELD/EXEMPTED/INCOMPLETE overrides;8. persist the result atomically;9. emit an audit event.Do not hard-code one university's formula. Define calculation policy interfaces/configuration so the SIS can support multiple programmes and schemes.

10. Term Result Model and Calculation Service
PROMPT 10.7 - Implement StudentTermResult
Implement StudentTermResult with exactly one record per term registration.Create a `TermResultService.calculate()` that aggregates the authoritative course results for the term. Calculate credits_registered, credits_earned, SGPA, CGPA, and result_status according to the programme/curriculum policy.Use Decimal arithmetic only. Never use binary float for marks, grade points, credits, SGPA, or CGPA. Quantize values to the precision used by the database.The service must distinguish calculation from publication. Calculation may update an unpublished result; publication stamps `published_at` and activates student visibility. Re-publication after correction must be auditable.

Client performs immediate numeric validation but server remains authoritative.

16. Calculation Policy Abstraction
Because assessment formulas differ across programmes and curricula, calculation rules should be configurable rather than embedded directly in model methods.
PROMPT 10.15 - Policy Engine
Design a calculation policy abstraction for Module 10.Provide interfaces/classes such as `InternalAssessmentPolicy`, `CourseResultPolicy`, and `TermGpaPolicy`. Policies may be selected by curriculum scheme/programme/course offering. Support component weightage, best-of-N rules, reduced marks, mandatory components, minimum internal/external thresholds, grace/moderation hooks, credit eligibility, repeat attempts, and SGPA/CGPA formula selection.All policy decisions must be deterministic, versionable, testable, and recorded sufficiently for later result audit. Avoid executable user-entered formulas unless securely designed and validated.

17. Transaction and Concurrency Requirements
Wrap mark batches and result calculations in transaction.atomic().
Use select_for_update() where concurrent result publication or correction could cause lost updates.
Enforce idempotency for repeated calculate/publish requests where possible.
Do not partially publish a batch if the business operation is defined as atomic.
Keep long-running report generation outside critical row locks.
Use database uniqueness constraints as the final defense against duplicate marks and duplicate attempts.
