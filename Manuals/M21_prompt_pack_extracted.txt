SIMS – Journals and Journal PublicationsImplementation Prompt Pack
Module 21 • Django • DRF • MySQL • Progressive Web Application
Purpose: a sequenced set of AI development prompts for implementing the supplied Journals and Journal Publications schema as an enterprise-grade SIMS module, including validation, security, APIs, PWA UX, testing, reporting, performance and deployment.
1. Architecture and Core Rules
Backend: Python, Django, Django REST Framework and MySQL 8.x/InnoDB; frontend: mobile-first React/TypeScript PWA.
Reuse existing SIMS authentication, employee, institution, campus, department, academic-year, RBAC, audit and document frameworks.
Every journal_publication specializes exactly one staff_activity; staff_activity_id is both publication primary key and foreign key.
Expected masters: journal_type, publisher, country, publication_type, indexing_agency and metric_type.
Normalize ISSN/eISSN and DOI before uniqueness checks; keep database constraints as the final integrity layer.
If publication_date is supplied, publication_year must equal its year. primary_author_position, when supplied, must be at least 1.
Journal defaults may prefill peer_reviewed/open_access, but publication-level values remain the historical truth.
Indexing verification and metric verification require separate authorization from ordinary data entry.
Protect referenced masters from unsafe hard deletion; use deactivation/archival according to SIMS policy.
Enforce organizational scope in backend querysets/actions; UI hiding alone is never authorization.

3. Execution Instructions
Run these prompts in order against the current SIMS repository. At each stage, first inspect existing conventions, state a concise implementation plan, implement only the requested scope, run checks/tests, and report changed files plus migration effects. Do not silently rename supplied columns or duplicate existing master tables.
4. Sequential AI Development Prompts
Prompt 1 — Repository and Dependency Analysis
Act as lead Django architect. Do not code yet. Inspect Django/DRF versions, settings, custom User/employee models, organizational scope, audit framework, API versioning, pagination/filtering/error conventions and frontend API patterns. Locate staff_activity, journal_type, publisher, country, publication_type, indexing_agency, metric_type, employee, academic_year, institution, campus and department. Compare the supplied SQL with existing models/migrations. Produce a dependency map, reuse plan, risks, migration strategy and exact file-by-file plan.
Prompt 2 — Django Models and Migrations
Implement models for journal, journal_publication, journal_publication_indexing and journal_metric, mapping every supplied field, FK, UNIQUE, CHECK and default. Model journal_publication as a one-to-one child of staff_activity with staff_activity_id as its database PK/FK. Faithfully enforce uniqueness of (staff_activity_id,indexing_agency_id); if the project Django version cannot use a composite ORM PK, use the minimum compatible ORM workaround while retaining the database uniqueness and documenting it. Use safe PROTECT/RESTRICT behavior, indexing_status choices, nonredundant indexes, migrations and tests.
Prompt 3 — Domain Validation and Normalization
Implement reusable validators for ISSN/eISSN syntax and normalization, DOI normalization including doi.org URLs, URLs, publication_date/publication_year consistency, configurable year bounds, metric_value >= 0, primary_author_position >= 1, verification provenance, quartile values where applicable and database-length limits. Add valid, invalid, duplicate and boundary tests. Server validation is authoritative.
Prompt 4 — Atomic Staff Activity + Publication Service
Create a transaction.atomic() service that validates the journal-publication activity type, creates/updates staff_activity, then creates/updates journal_publication with the same ID. Define one canonical synchronization rule for staff_activity.activity_title and paper_title. Prevent orphan records, identity replacement, employee reassignment and organizational-scope escalation. Define archive/delete behavior and test rollback paths.
Prompt 5 — Journal Master Management
Implement journal master CRUD with search by name/ISSN/eISSN/publisher/country and filters for type, active, peer-reviewed default and open-access default. Normalize identifiers, detect duplicates, prevent unsafe deletion, and provide an optimized autocomplete endpoint. Ordinary staff can search/select approved journals; authorized master-data roles manage them. Use select_related and add permission/uniqueness/query tests.
Prompt 6 — Publication REST API
Build versioned DRF endpoints for list, detail, create, update/patch, archive/delete, current-user publications and authorized employee publications. Filter by employee, institution, campus, department, academic year, journal, publication type, publication year, DOI, peer-reviewed, open-access, indexing agency/status and title. Add pagination, ordering, stable errors, select_related/prefetch_related, OpenAPI examples and strict object/scope authorization.
Prompt 7 — Indexing Verification Workflow
Implement publication indexing management. Permit multiple agencies but one row per agency. Data-entry users may submit CLAIMED records; designated verifier/research-admin roles control VERIFIED/DISCONTINUED transitions. Capture indexed_year, source_url and remarks, validate transitions, audit verification changes, expose dedicated/nested APIs, prefetch efficiently, and test duplicates plus permissions.
Prompt 8 — Journal Metrics
Implement journal_metric CRUD/history. Enforce journal + metric_type + metric_year uniqueness and non-negative metric values. Capture quartile, source_name, source_url and verified_at. Preserve historical years, provide ordered history and filters, separate entry from verification authority, and set verified_at only on explicit verification. Add comprehensive tests.
Prompt 9 — React/TypeScript PWA
Build mobile-first screens for My Publications, Add/Edit Publication, journal autocomplete, metadata, author/affiliation/abstract/keywords, indexing with verification badges, metric summary and publication detail. Use accessible responsive forms and loading/empty/error/permission states. Implement manifest/service worker using existing architecture. Cache shell/reference data safely, never stale permissions/verification. Preserve drafts where policy permits and only support offline writes with secure conflict-aware synchronization.
Prompt 10 — RBAC and Audit
Integrate with existing SIMS RBAC for own/scoped viewing, own record editing, journal master management, indexing verification, metric verification and reporting. Enforce permissions in backend querysets/actions. Audit creation, significant edits, archival/deletion and verification. Prevent data leakage through autocomplete, filters, exports and predictable IDs. Add cross-department/institution negative tests.
Prompt 11 — MySQL Performance
Use EXPLAIN on realistic publication lists, employee profiles, annual reports, journal lookup and indexing filters. Add only evidence-based composite indexes not already covered by PK/UNIQUE/FK indexes. Evaluate publication_year, journal_id, publication_type_id, scope fields and indexing_status. Optimize ORM joins/prefetch/pagination and add query-count tests. Report before/after plans and rationale.
Prompt 12 — Reporting and Export
Implement authorized reports by academic/publication year, employee, department, institution, journal, publication type, peer-reviewed/open-access, indexing agency/status and relevant quartile/metric year. Provide on-screen summaries and CSV/XLSX export through the project framework. Export scope must exactly match API authorization. Include generated time, filters and scope; test against leakage.
Prompt 13 — Automated Quality Gate
Test constraints/FK protection, normalization, date/year consistency, one-to-one identity, atomic rollback, journal uniqueness, indexing uniqueness/transitions, metric constraints, RBAC isolation, API search/filter/pagination, query counts and representative frontend integration. Run formatting/linting, Django checks, migration checks, backend tests and frontend tests/build. Fix failures rather than suppressing them and produce a concise quality report.
Prompt 14 — Security Review
Review broken object authorization, mass assignment, unsafe nested writes, injection, stored/reflected XSS in text/URLs, CSRF/CORS, search/autocomplete abuse, audit-log sensitivity, offline cache, export leakage and malicious URLs. Ensure verification cannot be forged through JSON fields. Add regression tests for confirmed weaknesses without weakening global security settings.
Prompt 15 — Deployment and Production Readiness
Verify migrations on staging, backup/rollback procedure, migration lock/downtime risk, environment configuration, PWA/static build, cache invalidation, API schema, logging/monitoring and health checks. Produce a deployment checklist covering backup, migrate, assets, service restart, smoke tests, permissions/log review and rollback. Do not perform destructive production actions without explicit authorization.
Prompt 16 — Final Traceability Review
Create a traceability matrix mapping every supplied SQL table/column/constraint to Django fields/migrations, API fields, UI controls and tests. Find schema drift, missing fields, redundant code, weak validation, authorization gaps, N+1 queries and untested workflows. Correct confirmed issues, rerun the quality gate, and prepare final developer plus administrator/user documentation.

journal_metric: journal, metric type/year/value, quartile, source provenance and verification timestamp.
