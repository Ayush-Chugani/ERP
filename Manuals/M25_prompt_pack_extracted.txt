SIMS – MODULE 25RESEARCH PROPOSALS
AI Implementation Prompt PackDjango + MySQL + DRF + React/TypeScript PWA
A sequential, production-oriented prompt pack for implementing the Research Proposals module inside the existing SIMS architecture. The prompts preserve the supplied schema while adding validation, workflow, security, reporting, testing and PWA requirements.
1. Core Architecture
ResearchProposal is a specialized one-to-one child of the existing StaffActivity supertype.
Reuse Employee, Department, FundingAgency, FundingType and ResearchStatus masters; do not duplicate them.
Use Django ORM/migrations, Django REST Framework, MySQL/InnoDB and the existing React + TypeScript PWA conventions.
All multi-table create/update/status operations must be transactional.
Enforce backend institution/campus/department scoping and object-level authorization.
Integrate existing audit, document, notification and export subsystems where available.
2. Supplied SQL Schema
CREATE TABLE research_proposal (
    staff_activity_id BIGINT UNSIGNED PRIMARY KEY,
    proposal_title VARCHAR(500) NOT NULL,
    principal_investigator_employee_id BIGINT UNSIGNED NOT NULL,
    department_id SMALLINT UNSIGNED NOT NULL,
    proposal_submission_date DATE NULL,
    funding_agency_id BIGINT UNSIGNED NULL,
    funding_type_id TINYINT UNSIGNED NULL,
    scheme_program_name VARCHAR(300) NULL,
    requested_amount DECIMAL(16,2) NULL,
    currency_code CHAR(3) NOT NULL DEFAULT 'INR',
    research_status_id TINYINT UNSIGNED NOT NULL,
    proposal_reference_number VARCHAR(150) NULL,
    project_objectives TEXT NULL,
    research_domain VARCHAR(300) NULL,
    expected_outcomes TEXT NULL,
    review_comments TEXT NULL,
    CONSTRAINT chk_research_proposal_requested_amount CHECK (requested_amount IS NULL OR requested_amount >= 0),
    CONSTRAINT fk_research_proposal_activity FOREIGN KEY (staff_activity_id) REFERENCES staff_activity(staff_activity_id),
    CONSTRAINT fk_research_proposal_pi FOREIGN KEY (principal_investigator_employee_id) REFERENCES employee(employee_id),
    CONSTRAINT fk_research_proposal_department FOREIGN KEY (department_id) REFERENCES department(department_id),
    CONSTRAINT fk_research_proposal_funder FOREIGN KEY (funding_agency_id) REFERENCES funding_agency(funding_agency_id),
    CONSTRAINT fk_research_proposal_funding_type FOREIGN KEY (funding_type_id) REFERENCES funding_type(funding_type_id),
    CONSTRAINT fk_research_proposal_status FOREIGN KEY (research_status_id) REFERENCES research_status(research_status_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

4. Sequential AI Development Prompts
Prompt 1 — Existing SIMS Repository Analysis
Act as a senior Django software architect. Inspect the existing SIMS repository before writing code. Locate StaffActivity, Employee, Department, FundingAgency, FundingType, ResearchStatus, Institution, Campus, AcademicYear, authentication/RBAC, audit logging, documents, notifications and the React PWA.Prepare an implementation map for Module 25. Identify reusable models, table/column names, PK/FK types, related_name conventions, deletion/soft-delete rules, serializers, viewsets, services, routes, frontend libraries, permission guards and test conventions. Compare the supplied SQL with existing code and flag duplicated fields, especially data already represented by StaffActivity. Do not create parallel master data or authentication systems.
Prompt 2 — Django Model and Migration
Implement ResearchProposal using existing SIMS conventions. Map staff_activity_id as a primary-key OneToOneField to StaffActivity; preserve all supplied field lengths/nullability; use DecimalField(max_digits=16, decimal_places=2); default currency_code to INR; use existing FK masters; set Meta.db_table='research_proposal'; and enforce requested_amount >= 0 in validation and a database CheckConstraint.Normalize currency codes, deliberately choose on_delete behavior for historical integrity, and add only justified indexes. If the project maps legacy tables with managed=False, follow that architecture. Return complete model/migration changes and explain decisions.
Prompt 3 — Domain Services and Validation
Create a service layer that validates the parent StaffActivity type, active/eligible PI, department/institution context, PI-department consistency where assignments exist, non-negative amount, currency, normalized strings, funding rules and controlled status transitions. Restrict review comments to authorized workflow roles. Implement create_proposal(), update_proposal(), change_status() and archive/delete behavior. Use transaction.atomic() whenever StaffActivity and ResearchProposal are changed together. Return structured DRF-friendly validation errors.
Prompt 4 — Co-Investigator Extension
Determine whether co-investigators are required. If yes, create a normalized ResearchProposalInvestigator model with proposal, internal employee and/or permitted external investigator identity, role, sequence order, responsibility and contact flag. Prevent duplicates and preserve order. Keep the supplied PI field authoritative unless the approved schema is intentionally revised. If outside scope, document the decision and do not add the table.
Prompt 5 — Proposal Status History
If no shared workflow history exists, implement immutable ResearchProposalStatusHistory with proposal, from_status, to_status, changed_by, changed_at and remarks, plus optional decision/reference metadata where justified. Status changes must occur through the service layer and write history in the same transaction. Build allowed transitions from actual ResearchStatus configuration, reject invalid transitions and expose a chronological timeline API.
Prompt 6 — DRF Serializers
Create compact list, detailed read, create/update write and status-change serializers. Include readable PI, department, funding agency/type, status and parent StaffActivity context while accepting stable IDs for writes. Validate fields/cross-field rules, protect audit/system fields, use Decimal without float conversion and design serializers/querysets together to prevent N+1 queries.
Prompt 7 — Secure REST API
Implement list, retrieve, create, update, archive/delete, dedicated status change, status timeline and related investigator/document endpoints using the project’s DRF conventions. Support pagination, ordering and filters for title, PI, department, funder, funding type, status, domain, submission-date range, StaffActivity academic/institution/campus context, currency and useful amount ranges. Use select_related/prefetch_related and scope every queryset by authenticated authorization.
Prompt 8 — RBAC and Object-Level Security
Integrate with existing SIMS RBAC. Reuse permission naming conventions for view/add/change/archive, workflow/review, export and documents. Support PI/self scope, department research coordinator/HoD scope, institutional research-office scope and administrator scope only where configured. Never trust client-supplied roles. Add tests proving URL/payload ID tampering cannot cross authorized scopes.
Prompt 9 — Master Data Lookup APIs
Reuse/expose lightweight lookup APIs for Employee/PI, Department, FundingAgency, FundingType and ResearchStatus. Return stable IDs and labels, normally active records only, server-side search for large lists, institutional scoping and caching where appropriate. If research_domain remains free text, offer suggestions; if a taxonomy already exists, propose a controlled migration rather than duplicating it.
Prompt 10 — React PWA Proposal List
Build a mobile-first React + TypeScript proposal list with responsive cards/table, server-side pagination, search, filter drawer, sorting, status, PI, department, funder, submission date and requested amount/currency. Show actions only when authorized. Reuse the design system and provide accessible controls, keyboard/touch support, loading skeletons, empty states and retry/error handling.
Prompt 11 — React PWA Create/Edit Form
Build a typed create/edit form with sections for proposal basics, PI/department, funding/scheme/amount/currency, objectives/outcomes, workflow status where permitted, review comments for authorized users, and optional documents/investigators. Load lookups asynchronously, show field-level API errors, preserve unsaved input on recoverable errors, warn on dirty navigation and handle money without floating-point corruption.
Prompt 12 — Proposal Detail and Timeline
Create a responsive detail page showing proposal metadata, StaffActivity context, PI/department, funding, objectives, expected outcomes, permitted review information, documents/investigators, audit metadata and chronological status history. Add role-aware edit/workflow/review/document/export/archive actions and confirmations for consequential transitions.
Prompt 13 — Secure Document Management
Integrate with the existing SIMS attachment subsystem. Support configurable categories such as proposal, budget, forwarding letter, ethics/approval, acknowledgement, review communication, revised proposal and sanction/rejection letter. Validate MIME/extension/size/name/permissions, store outside the public web root through the storage abstraction, and authorize every download. Reuse versioning where available.
Prompt 14 — Notifications and Workflow Events
Integrate configurable notifications for created/submitted, revision requested, resubmitted, status changed, approved/sanctioned, rejected, withdrawn and document-requested events. Determine recipients from roles/configuration, not hard-coded addresses. Use background jobs if present and trigger after successful transaction commit so delivery failure does not roll back valid data.
Prompt 15 — Dashboard, Reports and Exports
Create permission-scoped dashboard/report APIs and UI by academic year, department, PI, funder, funding type, status, domain, submission period and currency. Provide counts and requested-value totals, but never combine different currencies without explicit conversion rules. Reuse existing CSV/XLSX/PDF export infrastructure and enforce the same row-level permissions as the list API.
Prompt 16 — MySQL Performance Optimization
Analyze real ORM queries with EXPLAIN/EXPLAIN ANALYZE where supported. Evaluate indexes on PI, department, status, funding agency and submission date plus justified composites. Avoid redundant indexes already covered by PK/FK/index prefixes. Optimize select_related/prefetch_related and pagination, and report query-count/execution-plan evidence for material improvements.
Prompt 17 — Backend Automated Tests
Create Django/DRF tests for model constraints, amount/currency validation, parent activity type, PI/department rules, atomic transactions, status transitions/history, RBAC, object scoping, filtering/pagination/search, document permissions and concurrency-sensitive behavior. Include negative tests for cross-scope ID tampering, invalid FKs, negative amounts, malformed currency, oversized strings and mass assignment.
Prompt 18 — Frontend and PWA Tests
Add frontend tests for list/filtering, create/edit validation, detail view, workflow, permission-based actions, API errors and mobile layouts. Verify PWA caching policy: sensitive proposal API responses must not be indiscriminately cached for offline exposure, and service-worker updates must not preserve stale authorization state.
Prompt 19 — Security Hardening
Review authentication, authorization/IDOR, CSRF/CORS according to architecture, XSS-safe rendering, ORM usage, file upload security, rate limits where needed, secure headers, secrets, audit logs and error handling. Verify exports and document downloads enforce object-level permissions. Ensure logs do not unnecessarily contain confidential proposal documents or payloads. Fix findings and add regression tests.
Prompt 20 — Admin / Research Office Interface
Configure Django Admin or the existing internal administration UI with useful list_display, search_fields, list_filter, autocomplete/raw-ID fields and optimized get_queryset(). Do not allow admin screens to bypass domain workflow rules. Restrict access by business permission and institutional scope rather than assuming Django staff status grants unrestricted access.
Prompt 21 — Seed Data and Configuration
Prepare idempotent fixtures/data migrations/management commands for required module configuration. Reuse existing StaffActivityType, ResearchStatus, FundingType and permission records. Do not duplicate master rows because of label differences; prefer stable codes. Make seeding safe to rerun in development, testing and production deployment workflows.
Prompt 22 — API Documentation
Document all Research Proposal endpoints with the project’s OpenAPI/Swagger tooling, including authentication, permissions, request/response schemas, filters, pagination, status-change examples and validation errors. Document the atomic StaffActivity relationship and workflow rules. Use synthetic examples, not real confidential research data.
Prompt 23 — Deployment and Migration Plan
Prepare a safe deployment plan covering migration ordering, backup/rollback, seed/configuration order, backend deployment, frontend build, service-worker cache/version update, background workers if used and post-deployment checks. Make production data migrations idempotent and minimize blocking schema operations. Use commands appropriate to the actual SIMS deployment environment.
Prompt 24 — Acceptance and Integration Review
Perform an end-to-end acceptance review of Module 25. Verify schema fidelity; StaffActivity one-to-one integrity; validation; PI/department ownership; funding metadata; amount/currency handling; workflow history; documents; RBAC; APIs; reports; PWA responsiveness/accessibility; tests; security; performance; migrations and rollback.Run the full backend/frontend test suites, migration checks, lint/type checks and representative MySQL query-plan checks. Refactor toward existing SIMS conventions while preserving API/database compatibility.
