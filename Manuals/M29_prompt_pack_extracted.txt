1. Authoritative Database Schema
CREATE TABLE extracurricular_activity (
 staff_activity_id BIGINT UNSIGNED PRIMARY KEY,
 extracurricular_category_id SMALLINT UNSIGNED NOT NULL,
 event_name VARCHAR(500) NOT NULL,
 organizer_id BIGINT UNSIGNED NULL,
 institution_organization_id BIGINT UNSIGNED NULL,
 event_date DATE NULL,
 venue_name VARCHAR(250) NULL,
 city VARCHAR(120) NULL,
 state_id SMALLINT UNSIGNED NULL,
 country_id SMALLINT UNSIGNED NULL,
 award_recognition VARCHAR(500) NULL,
 activity_details TEXT NULL,
 FOREIGN KEY (staff_activity_id) REFERENCES staff_activity(staff_activity_id),
 FOREIGN KEY (extracurricular_category_id) REFERENCES extracurricular_category(extracurricular_category_id),
 FOREIGN KEY (organizer_id) REFERENCES organizer(organizer_id),
 FOREIGN KEY (institution_organization_id) REFERENCES external_organization(organization_id),
 FOREIGN KEY (state_id) REFERENCES state(state_id),
 FOREIGN KEY (country_id) REFERENCES country(country_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
2. Implementation Assumptions
Backend: Django + Django REST Framework; database: MySQL 8.x.
Frontend: React + TypeScript mobile-first Progressive Web Application.
extracurricular_activity is a subtype/detail record of staff_activity; its PK is also the FK to the parent.
Existing master tables and common SIMS services must be reused.
Authorization must be enforced at API and object level, not only in the UI.
Supporting documents should use the common attachment/evidence subsystem.
All implementation must include tests, query optimization, accessibility, documentation, and deployment checks.
