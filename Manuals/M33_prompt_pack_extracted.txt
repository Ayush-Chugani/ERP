1. Purpose of This Prompt Pack
This document provides a sequenced set of implementation prompts for building a production-grade centralized evidence and document management module inside the SIMS Django application. The prompts are intentionally modular so they can be executed one at a time, reviewed, tested, and committed incrementally.
Treat the supplied SQL schema as the functional baseline and preserve its relationships and audit intent.
Keep physical file storage behind file_object and a provider-neutral storage service; do not place file blobs directly in evidence_document.
Use transactions and row locking for version replacement and workflow-sensitive updates.
Enforce object-level confidentiality and organizational authorization on every metadata/file operation.
Keep historical versions immutable and auditable; never overwrite an old evidence file.
Use PWA caching conservatively so confidential evidence is not exposed from offline caches.
2. Recommended Execution Method
Run the Master Context Prompt first and keep it attached to every subsequent coding prompt.
Execute prompts in sequence. Prompts 1-5 establish architecture and data foundations; Prompts 6-16 implement domain behavior; Prompts 17-23 expose the module; Prompts 24-32 harden, test, document, and deploy it.
After each coding prompt, run migrations/checks, targeted tests, security tests, and code review before moving to the next prompt.
When the existing SIMS project already has a pattern for services, selectors, permissions, audit, storage, Celery, or DRF, adapt to that pattern rather than introducing a conflicting architecture.
Do not accept generated code that bypasses existing user_account, staff_activity, file_object, or lookup/master tables.

Central evidence metadata linked to any staff_activity record.
One-to-many immutable file versions with an explicit current version.
Configurable document type, evidence type, academic year, issuing organization, and confidentiality metadata.
Independent verification and approval workflows with responsible users, timestamps, remarks, and rejection reasons.
Optional tags for discovery and reporting.
Secure preview/download with authorization at request time.
Complete audit trail for create, upload, replace, metadata change, preview, download, verification, approval, deletion, restore, and denied access.
Soft deletion without loss of version or audit history.
Expiry monitoring, search, reporting, PWA integration, operational logging, and production deployment controls.

Area
Required Approach
Avoid

Public media URL or raw path exposure
Versioning

Authorization

UI-only hiding of buttons
Audit
Append-only evidence_document_audit events
Editable/deletable audit history
Workflow
Explicit service methods and transition rules

Deletion
Soft delete metadata; retain versions/audit
Hard delete on normal user action
PWA
Cache shell/static only for sensitive areas
Caching protected documents or signed URLs
Concurrency

max(version)+1 without locking

Appendix B - Key Design Decisions the Implementation Should Preserve
evidence_document is the business metadata and workflow aggregate; evidence_document_version is the immutable content history.
file_object owns physical/object-storage concerns. Evidence versions reference file_object rather than duplicating storage metadata.
current_version_number on the parent is a denormalized convenience and must agree with the current version selected by the service layer.
Verification and approval are separate workflows and should use explicit action services rather than unrestricted field updates.
Confidentiality is a runtime authorization concern in addition to a stored classification value.
PREVIEW and DOWNLOAD are security-relevant events and belong in the audit trail.
Soft deletion exists to preserve institutional evidence history and must not destroy version/audit records.
PWA support must improve usability without weakening document confidentiality or leaving sensitive cached artifacts after logout.
