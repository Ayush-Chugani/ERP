7. Migration Engineering Prompt
Generate migrations only for indexes not already satisfied. Prefer migrations.AddIndex with models.Index(fields=[...], name='...'). Keep each migration in the app owning the table and depend on the latest migration that establishes all referenced fields.
Respect Django/MySQL index-name limits. If an exact supplied name cannot be represented, report a controlled rename requirement rather than silently renaming it. For unmanaged or legacy tables, use the smallest safe RunSQL or SeparateDatabaseAndState solution and explain why. Forward migration must create only the intended indexes; reverse migration must remove only those indexes.
8. Redundancy and Query-Plan Prompt
Compare every requested index with PRIMARY KEY, UNIQUE, FK-supporting and existing composite indexes using MySQL leftmost-prefix rules. Do not automatically delete existing indexes.
Produce a redundancy-review table with requested index, existing candidate, exact ordered columns, coverage assessment, decision and evidence. Use EXPLAIN/EXPLAIN ANALYZE for representative safe SELECT queries where useful. Do not claim performance improvement solely because an index exists.
9. Verification Prompt
Run: python manage.py makemigrations --check; python manage.py check; clean-database migration; upgrade-path migration; affected unit/integration tests; and reverse-migration testing in a disposable database.
For every affected table, verify SHOW INDEX or INFORMATION_SCHEMA.STATISTICS output for index name, ordered columns and uniqueness. Confirm no accidental UNIQUE constraint was created. Return a pass/fail checklist and exact remediation for any mismatch.
10. Performance Validation Prompt
Select representative ORM queries corresponding to the supplied indexes and capture query plans on a non-production dataset of meaningful size. Record predicates, ordering, row counts and plans. Measure latency only under comparable conditions and never invent percentage gains.
Also document write/storage overhead and flag overlapping indexes for later DBA review. Recommendations must remain separate from required Module 18 implementation.

Return: files changed by app; migration names/dependencies; complete Module 18 reconciliation matrix; status of every supplied index; evidence for non-created indexes; database verification summary; Django check/test results; controlled deviations; and optional DBA recommendations.
Acceptance criteria: every supplied index is accounted for; composite order is exact; no business semantics changed; no known duplicate equivalent index introduced; custom RBAC remains authoritative; sensitive HR data is protected; forward/reverse migrations work; clean-install and upgrade-path tests pass; and physical MySQL metadata matches the approved implementation.
