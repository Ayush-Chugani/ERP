1. Source Database Definition
Use the following SQL definition as the authoritative starting point. Do not silently change column nullability, data types, foreign keys, or date-check semantics without documenting the reason and producing a migration strategy.
CREATE TABLE staff_professional_contribution (    staff_activity_id BIGINT UNSIGNED PRIMARY KEY,    professional_contribution_type_id SMALLINT UNSIGNED NOT NULL,    organization_id BIGINT UNSIGNED NULL,    journal_id BIGINT UNSIGNED NULL,    conference_event_id BIGINT UNSIGNED NULL,    programme_id SMALLINT UNSIGNED NULL,    course_id INT UNSIGNED NULL,    student_id BIGINT UNSIGNED NULL,    title_topic VARCHAR(500) NULL,    appointment_reference_number VARCHAR(150) NULL,    contribution_date DATE NULL,    start_date DATE NULL,    end_date DATE NULL,    number_of_reviews SMALLINT UNSIGNED NULL,    number_of_candidates SMALLINT UNSIGNED NULL,    contribution_details TEXT NULL,    outcome_details TEXT NULL,    CONSTRAINT chk_prof_contribution_dates CHECK (        end_date IS NULL OR start_date IS NULL OR end_date >= start_date    ),    CONSTRAINT fk_prof_contribution_activity FOREIGN KEY (staff_activity_id)        REFERENCES staff_activity(staff_activity_id),    CONSTRAINT fk_prof_contribution_type FOREIGN KEY (professional_contribution_type_id)        REFERENCES professional_contribution_type(professional_contribution_type_id),    CONSTRAINT fk_prof_contribution_org FOREIGN KEY (organization_id)        REFERENCES external_organization(organization_id),    CONSTRAINT fk_prof_contribution_journal FOREIGN KEY (journal_id) REFERENCES journal(journal_id),    CONSTRAINT fk_prof_contribution_conference FOREIGN KEY (conference_event_id)        REFERENCES conference_event(conference_event_id),    CONSTRAINT fk_prof_contribution_programme FOREIGN KEY (programme_id) REFERENCES programme(programme_id),    CONSTRAINT fk_prof_contribution_course FOREIGN KEY (course_id) REFERENCES course_catalog(course_id),    CONSTRAINT fk_prof_contribution_student FOREIGN KEY (student_id) REFERENCES student(student_id)) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
2. Architectural Interpretation and Guardrails
This table is a subtype/extension of staff_activity: staff_activity_id is both the primary key and a foreign key. Creation and deletion must therefore respect the parent activity lifecycle.
professional_contribution_type_id determines the semantic category of the contribution. Field requirements should be driven by configurable type metadata or a centralized validation policy, not scattered conditional code.
organization_id, journal_id, conference_event_id, programme_id, course_id, and student_id are optional contextual relationships. The SQL does not state that only one may be populated. Do not introduce an exclusivity constraint unless the business owner approves it.
The database enforces end_date >= start_date when both dates are supplied. The same rule must be repeated at Django form/serializer/service validation level to provide friendly errors before database rejection.
Unsigned numeric counts must never be negative. Django validators and serializer validation should explicitly reject negative values even if database column semantics also protect the data.
Use transaction.atomic() when creating or updating staff_activity and staff_professional_contribution together. Never leave orphaned parent activities after a child-validation failure.
All lookup/reference choices should use searchable selectors appropriate to dataset size. Avoid loading very large student/course/journal lists into a single unfiltered HTML select.
Apply institutional authorization: staff can manage their own records as permitted; designated reviewers/HoDs/administrators can verify, review, or manage records according to existing SIMS RBAC.
