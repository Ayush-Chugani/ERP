Module Scope
This module maintains independent student and employee root entities. It reuses common demographic and institutional reference masters through foreign keys, while deliberately avoiding inheritance from a generic person table. Authentication identities remain separate from domain profiles and may be linked explicitly only when access is required.

Architecture Guardrails
Keep student and employee as independent aggregate roots; do not introduce a generic Person superclass or shared database table.
Use a custom Django User model from the first migration. Keep login credentials and authentication state outside student and employee tables.
Use explicit optional one-to-one account links only for students or employees who require system access.
Enforce institution, campus, department, role, workflow, confidentiality, and record-level scope at both service and API layers.
Keep the module independently replaceable inside a plugin-ready modular monolith; expose stable service interfaces and avoid cross-app model imports where practical.
Use database constraints for invariants, service-layer validation for business rules, and transactions for multi-record workflows.
Never silently weaken supplied uniqueness, generated-column, composite foreign-key, or effective-date rules.
