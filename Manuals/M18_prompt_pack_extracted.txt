Purpose and implementation position
This pack instructs an AI coding agent or development team to implement the supplied performance indexes safely in the existing SIMS Django project. Performance indexes are a cross-cutting database concern. Do not create a new runtime business app solely for this module. Place each index on the Django model that owns the indexed table, generate migrations inside that model’s existing app, and coordinate deployment through the project migration workflow.
The governing rule is fidelity: preserve every supplied index name, column order, table ownership, existing constraint, and custom-user authorization behavior. An index migration must not rename tables, alter fields, change nullability, modify foreign keys, or rewrite business logic unless a separately approved prerequisite demands it.
How to use this pack
Run Prompt 0 once to establish repository facts and stop on structural mismatches.
Run Prompts 1 through 8 in order. Keep each change reviewable and migration-safe.
Use Prompt 9 for verification in a production-like database with representative data.
Run Prompt 10 before deployment and Prompt 11 after release.
Do not apply a destructive or blocking production migration merely to satisfy the prompt. Escalate conflicts with evidence.
Non negotiable guardrails
Do not create duplicate indexes already provided by primary keys, unique constraints, foreign-key indexes, model field db_index declarations, or previous migrations without documenting the decision.
Do not use raw RunSQL by default. Prefer migrations.AddIndex with models.Index unless the database capability requires a vendor-specific operation.
Never log, display, copy, or expose PAN, Aadhaar, banking, password, or authentication data while testing.
Use exact explicit index names. Confirm the target database permits every name and that names are unique in the required namespace.
Preserve leftmost-column order. Reordering composite fields changes query support.
Keep application behavior and API contracts unchanged; this module changes database access paths only.

Django apps

Custom user

Migrations
Generate one or more dependency-ordered migrations in owning apps. Explicitly handle cross-app dependencies.

Target MySQL or MariaDB with InnoDB and utf8mb4. Record the tested server and Django versions.
Soft deletion
Retain deleted_at in the exact supplied composite position. Do not convert to a partial index because MySQL lacks general partial indexes.

Plugins
Expose no new plugin contract unless the existing architecture requires a migration or health-check extension point.

Prompt sequence
Prompt 0 Repository discovery and stop gate
Objective: Map the existing codebase before editing.
You are implementing SIMS Module 18 Performance Indexes in an existing Django modular monolith. Inspect the repository and produce an evidence-based implementation map. Identify Django and database versions, settings modules, installed apps, custom user model, database routers, model-to-table mappings, migration heads, table naming overrides, existing indexes, unique constraints, foreign keys, soft-delete conventions, and test commands.For every supplied table, locate exactly one owning Django model and app. Compare model fields with the supplied column names. Flag missing tables, missing fields, renamed db_column values, unmanaged models, proxy models, swapped user models, and migration graph conflicts. Do not edit files yet. Stop if a table maps ambiguously, an index name exceeds the active database limit, or the current database is not the intended MySQL/MariaDB target.
Required outputs: Repository map; environment matrix; model-to-table mapping; existing-index inventory; blockers; proposed migration grouping.
Prompt 1 Canonical index manifest
Objective: Create a machine-reviewable source of truth for all requested indexes.
Create a canonical index manifest from the supplied specification. Each entry must include domain, app label, model name, db_table, exact index name, ordered Django field names, ordered physical column names, index purpose, likely query shape, sensitivity classification, existing equivalent index if any, and disposition: ADD, ALREADY_COVERED, NEEDS_REVIEW, or BLOCKED.Do not treat a wider or differently ordered composite index as automatically equivalent. Apply the leftmost-prefix rule. Distinguish an exact duplicate from partial coverage. Keep all 65 requested indexes accounted for and report the total by disposition.
Required outputs: Manifest file or structured report; count reconciliation; duplicate/coverage analysis; unresolved mapping list.
Prompt 2 Django model metadata
Objective: Represent approved indexes in their owning Django models.
For each manifest entry marked ADD, update the owning model Meta.indexes using models.Index(fields=[...], name='...'). Preserve the exact index name and field order. Use Django model field names in fields, not raw database column names. Respect db_column mappings. Do not add db_index=True when a named models.Index is required. Do not alter constraints, relationships, on_delete behavior, defaults, nullability, choices, managers, or authorization logic.If a model is unmanaged, explain whether state-only migrations, SeparateDatabaseAndState, or a database-owned migration is appropriate; do not guess. Keep formatting consistent with the project.
Required outputs: Model changes grouped by app; explicit list of skipped entries and reasons; static validation results.
Prompt 3 Migration generation and dependency design
Objective: Create deterministic, reversible schema migrations.
Generate Django migrations for the approved model index changes. Review every operation: it should be AddIndex or an explicitly justified alternative. Split migrations when necessary to respect app ownership, dependency ordering, deployment risk, or database locking constraints. Use exact index names. Ensure dependencies point to the current migration heads and include swappable_dependency(settings.AUTH_USER_MODEL) where genuinely required by existing model relationships.Do not combine unrelated field or constraint changes. Do not fake migrations. Do not edit historical migrations unless the repository policy explicitly requires a clean baseline and approval is recorded.
Required outputs: Migration files; operation-to-index reconciliation; dependency graph; reversibility notes; sqlmigrate output summary.
Prompt 4 Database compatibility and duplicate audit
Objective: Prove that the migration is valid for the target server.
Validate all index definitions against the actual MySQL or MariaDB version, InnoDB limits, character set, collation, index-name rules, maximum key length, nullable columns, and column data types. Query database metadata to identify exact, prefix-equivalent, redundant, or conflicting indexes. Pay special attention to long varchar columns such as names, organization names, bank names, entity names, and username.If a full-width index is not supported, stop and propose alternatives with tradeoffs; do not silently add prefix indexes or hashes. Document foreign-key-created indexes and unique indexes that may make a requested index redundant.
Required outputs: Compatibility matrix; database metadata evidence; duplicate/redundancy decisions; blocking risks and recommendations.
Prompt 5 Query alignment and repository integration
Objective: Confirm that index order matches real ORM workloads.
Search managers, services, selectors, repositories, admin filters, API filtersets, reports, scheduled jobs, and audit queries for filters, joins, ordering, and date ranges that correspond to each composite index. Map real QuerySets to candidate indexes. Identify low-selectivity leading columns, indexes used only for sorting, and supplied indexes that do not match current query order.Do not rewrite application queries merely to force index usage. Recommend a query change only when semantically equivalent, covered by tests, and separately listed for approval. Preserve tenant, campus, institution, and authorization scoping.
Required outputs: Query-to-index traceability matrix; uncovered hot queries; supplied indexes with weak workload evidence; optional separately scoped query recommendations.
Prompt 6 Automated schema and migration tests
Objective: Add tests that verify structure without coupling to implementation noise.
Implement tests appropriate to the repository. Verify that the Django model state contains every approved named index with exact field order. Add migration tests for forward application and reversal using a disposable database where the project supports them. Add database introspection assertions for exact names and column order on MySQL/MariaDB, guarded so unsupported local test engines do not create false confidence.Add checks for manifest count reconciliation and duplicate names. Never use production data or sensitive values in fixtures. Use synthetic PAN, Aadhaar, bank, login, and document metadata.
Required outputs: Test files; commands; expected results; engine-specific skips with justification; coverage of all approved indexes.
Prompt 7 Performance verification
Objective: Measure useful access-path changes rather than assuming improvement.
Select representative high-value queries from the traceability matrix. Create production-shaped, synthetic test data at meaningful cardinalities. Capture EXPLAIN or EXPLAIN ANALYZE where supported before and after indexes. Record access type, chosen key, key length, estimated and actual rows when available, filtered percentage, sort or temporary-table use, and latency distribution over repeated runs.Warm-up and measurement must be separated. Do not claim an improvement from one timing. Redact sensitive predicates. Treat write amplification, storage growth, buffer pressure, and slower bulk imports as costs. Do not force indexes in application code unless independently approved.
Required outputs: Benchmark protocol; before/after query plans; results table; storage/write-cost estimate; keep/remove/review recommendation per tested index.
Prompt 8 Security and privacy review
Objective: Ensure optimization work does not weaken protections.
Review all changes involving user_account, login_audit, password_history, employee_bank_account, employee_pan, employee_aadhaar, employee_document, employee_document_access_rule, employee_sensitive_access_audit, and file_object. Confirm that indexes do not introduce new endpoints, permissions, logs, exports, admin displays, or debug output. Verify that EXPLAIN capture and test fixtures contain no real identifiers, credentials, document keys, gateway references, or financial data.Preserve the existing custom-user authorization and scoped RBAC rules. Indexes improve lookup performance but never grant access; tests must still assert authorization boundaries.
Required outputs: Security checklist; sensitive-table test evidence; redaction confirmation; authorization regression results.
Prompt 9 Full verification gate
Objective: Run the complete quality gate in a production-like environment.
Run project checks, formatting/linting, type checks if configured, unit and integration tests, migration consistency checks, migration plan, sqlmigrate review, forward migration, metadata introspection, representative EXPLAIN tests, and reverse migration in a disposable production-like MySQL/MariaDB database. Reapply the migration after reversal and rerun critical tests.Compare the final database metadata to the canonical manifest. Fail the gate for a missing name, wrong order, duplicate operation, unintended schema drift, failed reversal, authorization regression, or unexplained test skip.
Required outputs: Command log summary; pass/fail table; final 65-entry reconciliation; exceptions requiring approval.
Prompt 10 Deployment plan
Objective: Prepare a safe rollout for index creation.
Produce a deployment plan based on table sizes, traffic, database version, replication topology, backup policy, maintenance window, and online DDL capability. Estimate risk for large attendance, audit, transaction, assessment, document, and login tables. Specify prechecks, backup/restore readiness, migration command, lock and replication monitoring, timeout thresholds, abort criteria, postchecks, and communication responsibilities.If normal Django AddIndex may cause unacceptable blocking, propose a vendor-supported online schema-change procedure and a state/database synchronization strategy. Do not execute production changes in this task.
Required outputs: Runbook; risk-ranked migration batches; monitoring queries; abort criteria; rollback method; ownership and approvals.
Prompt 11 Post deployment observation and cleanup
Objective: Confirm real production value after release.
After approved deployment, verify index presence, application health, error rates, lock waits, replica lag, database CPU and I/O, slow queries, index usage statistics where reliable, write latency, and storage growth. Compare representative query plans with the approved baseline. Observe for an agreed period before recommending removal of redundant legacy indexes.Never drop an index automatically. Any removal requires workload evidence, foreign-key review, a separate reversible migration, and explicit approval.
Required outputs: Post-deployment report; incident thresholds; observed plan changes; follow-up recommendations; separately approved cleanup candidates.

Technical implementation patterns
Standard Django model declaration
Use the owning model’s field names. If a ForeignKey named academic_year stores academic_year_id, declare 'academic_year' in models.Index fields; Django resolves the database column.
class Meta:    indexes = [        models.Index(            fields=['application_status', 'academic_year'],            name='idx_application_status',        ),    ]
Expected migration operation
migrations.AddIndex(    model_name='admissionapplication',    index=models.Index(        fields=['application_status', 'academic_year'],        name='idx_application_status',    ),)
Database introspection
Use Django connection introspection for portable assertions and INFORMATION_SCHEMA.STATISTICS for MySQL or MariaDB confirmation. Order rows by SEQ_IN_INDEX. Compare INDEX_NAME and COLUMN_NAME against the manifest. Parameterize queries and restrict access to schema metadata.
SELECT TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAMEFROM INFORMATION_SCHEMA.STATISTICSWHERE TABLE_SCHEMA = DATABASE()ORDER BY TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX;
